# Problem definition

What's the actual problem here that stops me from simply throwing it away? The problem is that they actually might be useful in the unspecified future 😅.

Once your induction hop displays some specific error it might be easier to look it up in manual you already own instead of first trying to find its exact model and then googling it.
Or for example in my case, every few weeks I need to run self-cleaning program for my dishwasher. To do so you need to click simultaneously two buttons for few seconds.
For some reason I'm not able to memorise those 2 buttons. I swear to God I feel like I'm clicking the right buttons, but it doesn't work until I check it in the manual.

So let's agree it might not be the wisest idea to blindly put those manuals in the garbage. Simple solution? Digitalize them. For every manual that you physically own there must exist online version that you could download.
Okay, but what would be the engaging content here? How to automate downloading manuals so that you can get rid of the physical ones? That doesn't seem particularly interesting.

Instead, my idea is to create a solution that:
- answers questions regarding your household appliances
- uses manuals you already own as a ground truth to answer the questions
- shows original fragments of manuals if needed

That basically describes the most common use for Large Language Models - RAG (Retrieval-Augmented Generation) process.
In the internet you could find many resources that show how to implement such process.
But most of them showcase rather straightforward implementations, while I believe my use case provides interesting twists and gotchas.

# System requirements

The general idea for RAG process is simple. In our case the scenario will look as follows:
1. User asks a question about household appliance
2. Some algorithm searches through all available manuals and select most relevant parts (relevant to the asked question)
3. Relevant parts of manuals go to LLM as context alongside the question
4. LLM answers the question based on the context

The application needs to perform these steps. On top of that I have few specific requirements:

a) I want to keep support only for Polish and English manuals. Why? Because most documents are in English, but for few devices I only have Polish manuals.
Additionally some manuals are multilingual and simply that would be useless to keep such duplicated information.

b) Manuals are documents that are organised into logical sections, e.g. Error Codes or Cleaning sections.
When we will load those documents into database we want to keep this structure, so that valid parts are loaded as context to LLMs.

c) I want this solution to use open-source tools. I hope that's self-explanatory.

d) In the final version I want this solution to work on-demand. It shouldn't use resources 24/7 because in real-world scenario I will use it periodically.
So the inference engine should be loaded once I send the query and then shut off after being idle for some time.

e) The system should show me as an attachment original chunks of manuals LLM used to answer the question. 
Just in case I would need some more details e.g. specific symbols like button icons.

# Architecture design

The architecture will be divided into 2 parts: ingestion pipeline and inference pipeline.

Ingestion pipeline will transform household appliances manuals to format that could be used to answer my questions.

Inference pipeline will handle the logic to take my question and transform it into relevant and meaningful answer.


## Ingestion pipeline

### 1. Download all household appliances manuals

In order to do it, I prepared CSV file with all my household appliances that contains 3 information: type of device (e.g. dishwasher), brand and model.
Having this I simply asked Claude Code to download manuals for all my devices, keeping in mind that there needs to be at least either English or Polish (or both) version of the manual.
That also required to properly set up access to a browser, not to run out of the tokens too fast.
The process took surprisingly long but it finished successfully and ended up with ~70 manuals in PDF format.

### 2. Parse PDF documents into structured text chunks

For this step I decided to use [Docling](https://github.com/docling-project/docling) that is open-source tool for processing documents.
It has rich support for PDF documents and can extracts text items, tables and more importantly, preserves document hierarchy (chapters/sections). 

### 3. Keep only Polish and English content

As mentioned earlier, the manuals might contain different languages and I only care about English and Polish chunks.
In order to filter out unnecessary chunks I used language-detection model available in [fast-langdetect library](https://github.com/LlmKira/fast-langdetect).

Once model detects neither Polish nor English chunk, it is removed from the document tree.

One technical note - short text chunks (\<20 characters) are kept because there is a higher chance for language-detection model error.

### 4. Prepare metadata for each text chunk

Each text chunk will be eventually loaded to a database to allow for lookup once user sends a query (more on that later).
To effectively search through such chunks it's useful to provide some additional information about the chunk like:
- source file the chunk comes from
- household appliance name
- brand
- model
- language

### 5. Resize structured chunks to fit Embedding Model

This point is crucial for further understanding. 
It wasn't mentioned earlier but the goal of processing these manuals' chunks is to end up with some kind of numerical representation.
In simple terms we need numerical representation to be able to perform some mathematical operations, e.g. to tell how to text chunks are similar to each other.
Embeddings are the answer for numerical representation that we look for.
We will use some kind of Embedding Model that will transform text to numeric vector.
These models are designed to have strict maximum input length, measured in tokens.
The model that I'm using has this limit set to 512 tokens.

As you can imagine our current text chunks that are split by logical structure of document can have very different length.
Some sections are shorter, but most are probably longer than 512 tokens.
That's why we need to resize them. We want to split oversized chunks and merge undersized ones.
While splitting too large chunks seems pretty obvious, I believe that merging too small might sound counterintuitive.

First, why to bother? Wouldn't it be easier to simply embed small chunks as they are?
Not really - because small chunks, like single sentence or short paragraph produce weak embeddings.
Simply put there's not enough semantic signal for embedding model to cling to.

Secondly, wouldn't that lead to chunks that contain very different information from manual? For example two short chunks from end of one section and beginning of next one.
Yes, that would suck indeed, but merging is constrained and it can only merge elements at the same level in the document hierarchy.
So it won't merge content across section boundaries.

And the good news is that, while it sounds a bit complex, it is quite easy to perform using Docling's `HybridChunker` class.

Plus, at this point we add additional metadata about each chunk that will be useful later:
- section path
- page numbers
- sequential chunk index (that will be used later to figure out easily which chunks are "neighbours" for specific chunk)

### 6. Create embeddings for each chunk

As mentioned in previous step we want to convert text chunks into embeddings.
In fact, in order to maximise chances for finding relevant manuals' pieces, we need two types of embeddings: dense and sparse.
Dense embeddings are used for semantic similarity search. They usually have low dimension (128-1024) and most likely all values are non-zero.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          
Sparse embeddings are used for exact keyword matching. For that reason they are high dimension (usually have size of the vocabulary) and only few values are non-zero.                                                                                                                                                                                  

We need those two types, because we want to do hybrid search i.e. combine semantic and term matching search.

For that purpose I used `BAAI/bge-m3` embedding model ([link](https://huggingface.co/BAAI/bge-m3)) as it's very popular choice, can produce both dense and sparse embeddings and supports both Polish and English.
Dense embeddings are 1024-dimensional.

### 7. Load text chunks, embeddings and metadata to vector database

The last step is to ingest all information that we worked on into Vector Database.
There are a few good open-source options to choose from. I decided to go with [Qdrant](https://github.com/qdrant/qdrant).
Why? Because it's one of the most popular vector databases and I didn't have a chance to work with it so far.
I worked with extension of PostgreSQL made for working with vectors called `pgvector` but I didn't enjoy much.
If you're interested about this topic I recommend you taking a look at [this article](https://alex-jacobs.com/posts/the-case-against-pgvector/). 

One technical note: some metadata fields will be used quite frequently, for example source file, language, brand, model, appliance name.
That's why I created keyword indexes based on it to allow efficient filtering.

### 2. Rephrase the query using small LLM 

### 3. Use Named Entity Recognition (NER) model to identify household appliance in the query

### 4. Create enbeddings using query

### 5. Use Hybrid Search to retrieve candidate chunks

### 6. Use Reranker Model to select most relevant chunks from the candidates

### 7. Fetch neighbouring chunks to provide additional context around top results

### 8. Prepare context based on best chunks and pass it to LLM

1. **The user query's language is detected to determine the response language.**
   - `fast-langdetect` classifies the query as Polish, English, or other
   - Non-PL/EN queries default to English
   - The detected language is passed downstream for language-aware filtering and response generation

2. **The query is optionally rephrased or contextualized for better retrieval.**
   - Controlled by `ENABLE_QUERY_REPHRASING` (default: on)
   - Model: Gemini 2.0 Flash via OpenRouter (lightweight, fast)
   - For follow-up questions with conversation history: the query is rewritten as a standalone question incorporating prior context
   - For standalone queries: the query is rephrased to be clearer and more specific for retrieval
   - The original query is preserved for NER detection; the rephrased version is used for retrieval and reranking

3. **Named Entity Recognition identifies appliances mentioned in the query to narrow the search scope.**
   - Three-stage cascading detection:
     1. Regex matching for model numbers (pattern: `[A-Z0-9][A-Z0-9\-]{3,}[A-Z0-9]`, score: 1.0)
     2. GLiNER-large-v2 NER model detects appliance-type entities (e.g., "washing machine", "dishwasher") with a 0.3 confidence threshold (score: from model)
     3. Keyword substring fallback against all known appliance labels (score: 0.5)
   - Regex and GLiNER results are combined; keyword fallback only runs if neither produced results
   - Detected appliances are deduplicated by brand/model, keeping the highest score
   - Detected appliances are resolved to their source PDF files via the appliance catalog
   - A Qdrant filter is built to restrict search to only those files (OR logic across matches)
   - Fallback: if no appliance is detected but previous conversation turns had detections, those are reused

4. **The query is encoded into dense, sparse, and optionally ColBERT vectors using the same embedding model as ingestion.**
   - BGE-M3 produces a 1024-dim dense vector, a sparse lexical vector, and optionally ColBERT multi-vectors for the query
   - Using the same model for queries and documents ensures compatible vector spaces

5. **Hybrid search retrieves candidate chunks using a confidence-aware dual-path strategy.**
   - Two (or three, with ColBERT) parallel prefetch legs run in Qdrant, fused via Reciprocal Rank Fusion (RRF):
     - Dense search: cosine similarity on the 1024-dim vectors
     - Sparse search: lexical matching on the sparse vectors
     - ColBERT search (optional): late-interaction MaxSim on multi-vectors
   - Retrieval limit: 40 candidates per search leg
   - NER confidence determines the search strategy:
     - High confidence (max NER score >= 0.6): scoped retrieval only (filtered to detected appliance files)
     - Low confidence or no detection: both scoped and global (unfiltered) searches run, results are merged and deduplicated
   - Output: up to 40 unique candidate chunks with RRF-fused scores

6. **A cross-encoder reranker rescores candidates and selects the most relevant chunks.**
   - Model: BGE-Reranker-v2-m3 (`BAAI/bge-reranker-v2-m3`)
   - Each candidate is jointly encoded with the query as a `[query, chunk_text]` pair
   - The cross-encoder produces normalized relevance scores (0–1), which are more accurate than bi-encoder similarity
   - Two selection modes (configurable via `RERANK_MODE`):
     - `top_k` (default): return the best 5 results regardless of score
     - `threshold`: return only results with score >= 0.5, capped at 5

7. **Neighbouring chunks are fetched to provide additional context around top results.**
   - For each reranked result, adjacent chunks (chunk_index ± 1) from the same source file are retrieved from Qdrant
   - Neighbours already present in the top results are excluded
   - Controlled by `FETCH_NEIGHBOURS` (default: on) and `NEIGHBOUR_WINDOW` (default: 1)

8. **Retrieved chunks are formatted into a numbered context block for the LLM, enriched with neighbour context.**
   - Each chunk is wrapped with its source metadata:
     ```
     [Source N: filename.pdf, Section: path, Pages: X, Y]
     <preceding neighbour text, if available>
     <chunk text>
     <following neighbour text, if available>
     ```
   - Neighbour chunks are labeled as `[Preceding context]` / `[Following context]` but are not listed as separate sources
   - A parallel list of source info dictionaries is built for citation rendering in the UI

9. **The LLM generates an answer grounded in the retrieved context with source citations.**
   - Model: Claude Sonnet 4.6 via OpenRouter API (through LlamaIndex)
   - System prompt instructs the model to: answer in the query's language, base answers only on provided context, cite sources using `[Source N]`, and state when information is unavailable
   - Conversation history (last 3 turns) is included in the prompt for multi-turn coherence
   - Max output: 2048 tokens

10. **The response is rendered in the Chainlit UI with citations and original PDF page images.**
    - Rephrased query is displayed when it differs from the original
    - Detected appliances are shown with NER confidence scores
    - A note is shown when low NER confidence triggered a global fallback search
    - Source citations list file, section path, page numbers, and relevance score
    - Expandable side panels show the full retrieved text and metadata for each source
    - Up to 5 original PDF pages are rendered as images using `pypdfium2` (deduplicated across sources)
