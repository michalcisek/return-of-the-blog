# Problem definition

What's the actual problem here that stops me from simply throwing it away? The problem is that they actually might be useful in the unspecified future 😅.

Once your induction hop displays some specific error it might be easier to look it up in manual you already own instead of first trying to find its exact model and then googling it.
Or for example in my case, every few weeks I need to run self-cleaning program for my dishwasher. To do so you need to click simultaneously two buttons for few seconds.
For some reason I'm not able to memorise those 2 buttons. I swear to God I feel like I'm clicking the right buttons, but it doesn't work until I check it in the manual.

So let's agree it might not be the wisest idea to blindly put those manuals in the garbage. Simple solution? Digitalize them. For every manual that you physically own there must exist online version that you could download.
Okay, but what would be the engaging content here? How to automate downloading manuals so that you can get rid of the physical ones? That doesn't seem particularly interesting.

Instead, my idea is to create a solution that:
- answers questions regarding your household appliances
- uses manuals you already own as a ground truth to answer the questions
- shows original fragments of manuals if needed

That basically describes the most common use for Large Language Models - RAG (Retrieval-Augmented Generation) process.
In the internet you could find many resources that show how to implement such process.
But most of them showcase rather straightforward implementations, while I believe my use case provides interesting twists and gotchas.

# System requirements

Let's specify some more general requirements about this system aside from "answering questions about the devices I own using manuals about them".

a) First of all I want to keep support only for Polish and English manuals. Why? Because most documents are in English, but for few devices I only have Polish manuals.
Additionally some manuals are multilingual and simply that would be useless to keep such duplicated information.

b) Manuals are documents that are organised into logical sections, e.g. Error Codes or Cleaning sections.
When we will load those documents into database we want to keep this structure, so that valid parts are loaded as context to LLMs.

c) I want this solution to use open-source tools. I hope that's self-explanatory.

d) In the final version I want this solution to work on-demand. It shouldn't use resources 24/7 because in real-world scenario I will use it periodically.
So the inference engine should be loaded once I send the query and then shut off after being idle for some time.

e) The system should show me as an attachment original chunks of manuals LLM used to answer the question. 
Just in case I would need some more details e.g. specific symbols like button icons.

# Architecture design

The architecture will be divided into 2 parts: ingestion pipeline and inference pipeline.

Ingestion pipeline will transform household appliances manuals to format that could be used to answer my questions.

Inference pipeline will handle the logic to take my question and transform it into relevant and meaningful answer.


## Ingestion pipeline

#### 1. Download all household appliances manuals

In order to do it, I prepared CSV file with all my household appliances that contains 3 information: type of device (e.g. dishwasher), brand and model.
Having this I simply asked Claude Code to download manuals for all my devices, keeping in mind that there needs to be at least either English or Polish (or both) version of the manual.
That also required to properly set up access to a browser, not to run out of the tokens too fast.
The process took surprisingly long but it finished successfully and ended up with ~70 manuals in PDF format.

#### 2. Parse PDF documents into structured text chunks

For this step I decided to use [Docling](https://github.com/docling-project/docling) that is open-source tool for processing documents.
It has rich support for PDF documents and can extracts text items, tables and more importantly, preserves document hierarchy (chapters/sections). 

#### 3. Keep only Polish and English content

As mentioned earlier, the manuals might contain different languages and I only care about English and Polish chunks.
In order to filter out unnecessary chunks I used language-detection model available in [fast-langdetect library](https://github.com/LlmKira/fast-langdetect).

Once model detects neither Polish nor English chunk, it is removed from the document tree.

One technical note - short text chunks (\20 characters) are kept because there is a higher chance for language-detection model error.

#### 4. Prepare metadata for each text chunk

Each text chunk will be eventually loaded to a database to allow for lookup once user sends a query (more on that later).
To effectively search through such chunks it's useful to provide some additional information about the chunk like:
- source file the chunk comes from
- household appliance name
- brand
- model
- language

4. **The filtered document is split into chunks that respect its logical structure.**
   - Docling's `HybridChunker` performs a two-pass algorithm: first splits oversized elements, then merges undersized ones
   - Maximum chunk size is 512 tokens (aligned to the BGE-M3 tokenizer)
   - Section hierarchy is preserved — chunks don't cross chapter/section boundaries
   - Tables are kept as atomic units and never split
   - Each chunk receives metadata: section path, page numbers, source file, appliance info, and a sequential chunk index

5. **Chunks undergo a second language filter to catch any remaining foreign-language content.**
   - Merged chunks (e.g., tables combined with surrounding text) may contain foreign text that passed the first filter
   - Chunks detected as neither Polish nor English are discarded

6. **Dense, sparse, and optionally ColBERT embeddings are generated for each chunk in a single forward pass.**
   - Model: BGE-M3 (`BAAI/bge-m3`), which natively supports both Polish and English
   - Dense vectors: 1024-dimensional, used for semantic similarity search
   - Sparse vectors: lexical weight vectors, used for keyword-style BM25 matching
   - ColBERT vectors: multi-vector token-level embeddings (1024-dim per token), used for late-interaction matching — disabled by default (`ENABLE_COLBERT = False`), requires collection re-creation when toggled
   - Texts are processed in batches of 32

7. **Chunks, embeddings, and metadata are upserted into the Qdrant vector database.**
   - Collection `agd_manuals` stores dense, sparse, and optionally ColBERT vectors per point
   - Point IDs are deterministic (UUID5 from `source_file:chunk_index`), enabling idempotent re-ingestion
   - Keyword indexes are created on `source_file`, `language`, `brand`, `model`, and `appliance_name_pl` for efficient filtering
   - An integer index on `chunk_index` supports neighbour chunk lookups during inference
   - Already-ingested files are skipped by default (can be overridden with `--no-skip`)
   - Points are upserted in batches of 100 (or 10 when ColBERT is enabled), with automatic batch-halving on payload-too-large errors
